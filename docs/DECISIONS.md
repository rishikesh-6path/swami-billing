# DECISIONS

One dated paragraph per decision. Newest at the bottom. Dependency additions go here with the reason.

2026-10-01 — Electron 37+ with built-in `node:sqlite` instead of better-sqlite3. Reason: zero native modules, no ABI rebuild step, nothing to compile on the shop PC. Trade-off: slightly different API from better-sqlite3 (DatabaseSync/StatementSync); wrap it once in `packages/core/src/db/connection.ts`.

2026-10-01 — No ORM. Reason: ~25 tables, accounting queries must be auditable as SQL, and ORM migrations fight hand-tuned schemas. Repositories use prepared statements and zod row mappers.

2026-10-01 — Money as integer paise, quantity as integer thousandths. Reason: Busy shows 2-dp money and up to 3-dp quantity (e.g. 127.05 Metre); floats would break golden-file equality.

2026-10-01 — Vouchers are never hard-deleted. Reason: GSTR-1 table 13 requires gap-free document numbering and cancelled counts; audit trail for the CA.

2026-10-01 — Markdown-in-repo tracking (TASKS.md, SESSION_LOG.md) instead of GitHub Issues. Reason: single builder; keeps every Claude Code session free of issue-tracker MCP overhead.

2026-10-01 — UX principle: the users are non-technical shop staff, so every screen uses plain language (no database, schema, IPC or stack-trace wording), large readable text and click targets, and errors that say what happened and what to do next. Technical details (DB path, schema version) live in a collapsed "About this computer" panel. Busy's own terms (Sales, Receipt, Ledger) are kept because staff already know them.

2026-10-01 — Electron version correction: Electron 37 bundles Node 22.16, not Node 24 (Node 24 starts at Electron 40). Pinned `electron@^44` (Node 24.18) so the runtime matches the "Node 24" assumption. `node:sqlite` is available in both. Tooling (tests, scripts) only needs Node >=22.13 (`engines`), which is what the cloud container has.

2026-10-01 — electron-vite for building main/preload/renderer: one config, HMR, ESM main. Constraints: `@shopledger/core` (TypeScript source) must be bundled, not externalized; preload must be CJS (`.cjs`) and bundle zod because a sandboxed preload cannot require node_modules. Vite pinned to 7 (electron-vite 5 peer range), `@vitejs/plugin-react` 5, TypeScript ~6.0 (typescript-eslint supports <6.1), `@types/node` 22.

2026-10-01 — pnpm 10 skips dependency install scripts: `onlyBuiltDependencies: [electron, esbuild]` is set. If `apps/desktop/node_modules/electron/dist` is missing after `pnpm i`, run `node apps/desktop/node_modules/electron/install.js`.

2026-10-01 — SQLite pragmas: WAL, foreign_keys=ON, `synchronous=FULL` (not NORMAL) so a power cut cannot lose a committed bill (KICKOFF success criterion 3), busy_timeout 5000. Integrity check on every open; failure shows a plain-language dialog and quits without touching the file.

2026-10-01 — Migrations are loaded from a directory passed in by the caller, never via bundler globs, so `packages/core` stays plain-Node. Each migration records a sha256 checksum; editing an applied file or opening a database newer than the app is an error. Packaged location (`process.resourcesPath/migrations`) is wired in P5-04.

2026-10-01 — Dependencies added in Phase 0, with reason: typescript, eslint + @eslint/js + typescript-eslint + eslint-plugin-react-hooks + globals (lint incl. architecture rules: no Electron in core, no Node/core in renderer), prettier (formatting hook), vitest (core tests), fast-check (ledger invariants, KICKOFF section 10), @playwright/test (Electron E2E), electron, electron-vite, vite, @vitejs/plugin-react, react, react-dom (UI), zod (IPC validation), @types/node, @types/react, @types/react-dom.

2026-10-01 — Linux/CI gotcha: running Electron as root needs `--no-sandbox` (E2E passes it when uid is 0; for `pnpm dev` set `ELECTRON_DISABLE_SANDBOX=1`), and a headless box needs a virtual display (`pnpm e2e` wraps in `xvfb-run` when DISPLAY is unset).

2026-10-01 — Open questions resolved by the builder (owner asked to keep development moving; revisit any of these later): OQ-1 one company per database, the importer takes one export directory per company, GSTIN optional on the company. OQ-2 no orders, material issue/receive or batch tracking in v1. OQ-3 build both A4 and 80 mm thermal templates, printer chosen in settings. OQ-4 include GSTR-1 Table 4 (B2B) in v1; the data model carries party GSTIN anyway. OQ-5 tax per line rounded half away from zero in paise, grand-total round-off posted to a Round Off account. OQ-6 import FY 2026-27 plus opening balances only. OQ-7 owner closes the day; staff cannot edit or cancel vouchers dated on or before the last closed day.

2026-10-01 — Rounding: all money/quantity division rounds half away from zero (identical to round-half-up for positive amounts, symmetric for negative sundries and reversals), implemented with integer arithmetic only in `packages/core/src/money.ts`.

2026-10-01 — No Busy XML sample exists in the repo, so P1-01 (importer) is deferred until real export files are available; work proceeds on schema, posting engine and reports, which do not depend on Busy's file format.

2026-10-01 — Schema deviations from KICKOFF §6 (migration 0002): `voucher_series.next_no_per_fy` json replaced by a `voucher_counter` table (type, series, fy, last_no) so gap-free numbering is a plain row update inside the insert transaction; `journal_line` and `stock_movement` gain `is_reversal`; `voucher` gains `ref_voucher_id` (credit/debit notes must reference the original invoice) and `voucher_item` freezes `hsn`. DB triggers block deleting vouchers/journal lines/stock movements/audit rows and updating journal lines, stock movements and audit rows, and freeze voucher identity; balanced debits=credits is enforced in the posting engine because SQLite has no deferred constraints.

2026-10-01 — Tooling note: `.claude/settings.json` denies Edit/Write on `packages/core/migrations/0*`, which also blocks writing the content of a brand-new migration with those tools. New migration files are created via shell heredoc after `pnpm migrate:new`; applied files are never edited (the runner also checks sha256). Consider narrowing the deny rule.

2026-10-01 — Review fixes to the posting engine (ledger-reviewer pass). CGST and SGST are now each computed as taxable x rate / 2 rounded to the paisa, so they are always equal (replaces "round total tax once and give the odd paisa to CGST"); revisit with the CA under OQ-5 and when the GST Summary golden file exists. Cancel is refused in a locked financial year. Returns and credit/debit notes must reference a posted original invoice of the matching type dated on or before the note. Sales require an HSN of 4-8 digits. Tax mode must match the sale type when one is given, and an exempt sale freezes tax rate 0 on its lines. A line's unit must be the item's unit, and whole-number units reject fractional quantity. A taxable discount larger than its lines is rejected. Dates must be real calendar dates. `postVoucher(..., { legacyImport: true })` skips only the reference and HSN checks for the Busy importer.

2026-10-01 — Open, needs real Busy data: (a) whether Busy rounds the discounted unit price to the paisa before multiplying by quantity (the engine does, matching the stored `price_paise` column) or rounds once on the line amount; (b) the importer must keep Busy's original voucher numbers, which the internal gap-free counter cannot do today, so P1-01 must add an explicit-number path (and a gap report) rather than renumbering; (c) entry vouchers do not yet check that a receipt/payment has a cash or bank leg (P3-03).

2026-10-01 — Scope change: ShopLedger is a standalone system and Busy is reference only. Dropped: Busy XML importer, golden-file matching against Busy, reconciliation doc, `pnpm recon`, shadow-month. The two open Busy questions are closed: discounted unit price is rounded to the paisa then multiplied by quantity (as stored in `price_paise`), and voucher numbers come from the internal gap-free counter. Added: CSV import for items and parties, and a demo data seeder. TASKS.md is renumbered accordingly.

2026-10-01 — PIN hashing uses built-in `node:crypto` scrypt (N=2^15, per-user random salt) instead of argon2id: argon2 needs a native module and the stack is zero native modules. A 4-6 digit PIN is weak against offline attack either way, so the real protection is the single-PC deployment and lockout after repeated failures.

2026-10-01 — Reports review (ledger-reviewer pass #2). Place of supply (`voucher.pos_state_code`) and the party GSTIN (`party_gstin`) are frozen on each item voucher at posting (migration 0004): local bills use the shop's state, interstate bills need the customer's state (and it must differ from the shop's), exempt bills use the customer's state or the shop's. Reports read the frozen values, so editing a customer later never reclassifies an old invoice. The shop state (`company.state_code` setting) is required before billing; there is no silent default. GSTR-1: credit notes follow the invoice they refer to (registered = cdnr; large inter-state unregistered = cdnur; small unregistered reduce table 7 and are not listed); nil-rated and exempt supplies go to table 8 together because the voucher does not record which of the two applied; table 13 counts sales, sales-return and credit-note series. Entry-style credit/debit notes (no item lines) carry no GST breakup, so they are for non-GST adjustments only; GST corrections must use Sales Return / Purchase Return. All purchase tax is treated as eligible input credit.

2026-10-01 — Financial statements policy: stock is valued at weighted-average cost (opening stock + purchases less purchase returns at the returned price), inactive items still count; negative stock is valued at zero. Income and expense accounts start every financial year at zero in the trial balance and account ledger; profit of earlier years appears as "Profit and loss brought forward". The balance sheet is cumulative from the start of the books and shows any unbalanced opening entries as a separate "Difference in opening balances" line instead of hiding it. An opening balance in the outstanding report is treated as the oldest bill and aged from the start of the first financial year.

2026-10-01 — Known limitation: a cancelled voucher disappears from every report for its original date, including a period already filed with the GST portal. After filing, use a Sales Return instead of cancelling; the period lock added with day close (owner-set "books closed through" date) enforces this by refusing posts and cancels on or before that date. Table 13 uses MIN/MAX number within the period, so a back-dated voucher can make the range wider than the count.

2026-10-01 — Stock Journal and Physical Stock are stock-only vouchers: they post `stock_movement` rows and `voucher_item` lines for display but no journal lines, because stock is valued by the weighted-average method at report time (a count difference or a conversion changes closing stock, and so profit, automatically). This is the one exception to "every voucher posts balanced journal lines"; the invariant tests exempt exactly these two types. Stock-journal receipts need a cost per unit so valuation stays right; found stock from a physical count is valued at the item's average cost.

2026-10-01 — Voucher modify = cancel the original and post a linked replacement (`modified_from_id`) in one transaction; the replacement takes the next number. Refused when returns or notes already reference the bill. Receipts must debit cash/bank, payments credit it, contras stay within cash/bank, and journals and notes may not touch cash/bank. Returns cannot exceed the original quantity less earlier returns. Migration 0005 rebuilt `voucher_series` (its CHECK list gained the two stock types) using deferred foreign keys.
